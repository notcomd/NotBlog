> 关联提交：c816f516（权限树）/ 96699123（角色授权 API + JWT claim + 网关本地验证）
> 本文档是 96699123 的后续阶段：把「URL→权限码映射 + 网关集中判定」回收，改为各服务端点标注权限码、读 JWT `permissions` claim 本地自验。

## 一、现状诊断

### 当前权限链路（网关集中制）

```
客户端 --Bearer JWT--> YARP 网关
    ├─ UseAuthentication（JWT 校验）
    ├─ PermissionFilterMiddleware：URL→权限码（PermissionRouteMap，Mappings 106 条）
    │     码命中 → 本地前缀段匹配 JWT permissions claim（96699123 起）→ 403/放行
    │     无 claim（旧 token）→ 回退 HttpPermissionServiceClient / ConfigPermissionServiceClient 远程校验
    │     未映射路径 → DefaultPolicy=Deny 403
    ├─ UserContextTransform：注入 X-User-Id / X-User-Roles / X-Data-Scope（先 Remove 防伪造）
    └─ YARP 转发（32 条 Route）
服务端：组级 RequireAuthorization()（只认证，不鉴权）+ 内部业务判定（IsAdmin 等）
```

支撑机制（全部为网关权限体系服务）：PermissionMappingStore（Redis + JSON 双层）、PermissionMappingInitializer（启动拉取替换）、PermissionMappingRefresher（轮询）、PermissionUpdatedEventHandler（RabbitMQ 事件刷新）、Identity 侧 `/api/identity/permission/permission/mappings` + `check-and-scope`/`check`/`datascope` 端点（InternalApiKeyFilter + GATEWAY_INTERNAL_API_KEY 配对）、双源 appsettings（网关 `PermissionRoutes.Mappings` ↔ Identity `PermissionMappings`，各 106 条）。

## 二、设计原则

1. **权限判定与端点同处一地**：服务端每个受保护端点/端点组声明所需权限码（显式 `RequirePermission("api:x:y")` 或组约定 `RequireResourcePermissions("api:x")` 按 HTTP 方法派生），端点即契约，无第二张映射表。
2. **判定纯本地**：读 JWT `permissions` claim（Identity 签发快照），`PermissionCodeMatcher` 前缀段匹配（授权目录码自动放行子孙，与 Identity PermissionChecker 同规则）。零网络回调、零 Redis 依赖。
3. **身份可信源唯一**：服务端认证（JwtBearer）→ ClaimsPrincipal → 权限/角色/用户全部取自此。网关不再注入也不可信任何 X-User-* 头（S-02 已证明服务端不依赖）。
4. **未标注 = 维持现状**：公开端点（登录/注册/验证码/OAuth/健康检查/SignalR Hub/文件下载）不标注不认证；仅认证端点（组级 RequireAuthorization）不标注 = 保持「登录即可用」；业务管理端点按网关 106 条映射逐条对齐标注，不丢管控。
5. **认证去留**（决策点 D1）：网关认证层一并移除（透明网关，推荐）——五服务均已自带 JwtBearer + [Authorize]/组 RequireAuthorization，401 语义（Challenge + WWW-Authenticate）一致，前端无感；省掉网关重复验签与 header 注入，代码删除最彻底。
6. **兼容旧 token**：无 `permissions` claim 的旧签发 token 命中标注端点 → 401 Challenge 引导重登（一次升级窗口，不静默放行）。

## 三、目标架构

```
客户端 --Bearer JWT--> YARP 网关（透明：仅路由转发，32 条 Route 不变）
服务端（各服务独立）：
    JwtBearer 认证 → RequireAuthorization（认证）→ PermissionEnforcementMiddleware（鉴权，仅对标注端点）
    标注：MapGroup("...").RequireResourcePermissions("api:x")   ← 组级约定派生 read/create/update/delete
          endpoint.RequirePermission("api:x:y")                  ← 端点级显式（组内个别端点不同码时覆盖）
    判定：context.User permissions claim → PermissionCodeMatcher 前缀段匹配 → 通过 next / 401 / 403 JSON
```

### 3.2 判定中间件行为（复用 96699123 起草、未提交的 JWToken 扩展，正式纳入）

- `RequirePermissionAttribute`：端点元数据标注所需权限码（多标注 = 命中其一放行）
- `RequireResourcePermissions(prefix)`：组级约定，未显式标注的端点按 HTTP 方法追加 `{prefix}:read/create/update/delete`
- `PermissionEnforcementMiddleware`（`UsePermissionEnforcement`，置于 `UseAuthorization()` 之后）：
  1. 端点无标注 → next（仅认证管控不变）
  2. 标注端点未认证 → 401 Challenge
  3. 认证但无 `permissions` claim（旧 token）→ 401 Challenge（引导重登）
  4. 有 claim → `PermissionCodeMatcher.HasPermission` 前缀段匹配 → 不中 403 JSON
- `PermissionCodeMatcher`：`code==a || code.StartsWith(a+":")` + `ParsePermissionClaim`（逗号拆分 OrdinalIgnoreCase）
